# Existing Kibana clients

Researched on 2026-09-26. This is source and registry inspection, not a runtime certification. No client implementation or live Kibana tests were performed.

## Conclusion

A small, well-tested Rust client for common automation has a defensible purpose. The gap is narrower than "Rust has no Kibana client": `kibana-sync` is active and reusable, but its API is built around moving Kibana artifacts. A new project should earn its place through a clear compatibility policy, useful Rust request and response types, and common administrative APIs. Broad endpoint coverage already exists in Python.

The evidence favors starting with a curated API and shared HTTP behavior. Generating every endpoint is technically plausible, but Elastic's own Go implementation shows that schema repair becomes a separate maintenance project. These are judgments from the inspected projects below, not measured development estimates.

## Rust: reuse if the requirement is artifact synchronization

`kibana-sync` lives in the Kibana Object Manager workspace. The crate is separate from the CLI and accepts explicit configuration. Its transport has authentication, request and connect timeouts, concurrency limiting, space-scoped routing, version discovery, and capability checks. That is meaningful existing work. Source inspection found no OpenAPI generation pipeline for its endpoint modules. [Crate manifest](https://github.com/VimCommando/kibana-object-manager/blob/d75a3984b1875fb2d06afb9ab209a362d770d815/crates/kibana-sync/Cargo.toml), [client source](https://github.com/VimCommando/kibana-object-manager/blob/d75a3984b1875fb2d06afb9ab209a362d770d815/crates/kibana-sync/src/client/kibana.rs).

The public endpoint modules are extractors and loaders for saved objects, spaces, agents, tools, skills, and workflows. Its exported abstractions also include ETL, dependency discovery, manifests, and filesystem or in-memory bundles. The inspected module tree does not include alerting, connectors, cases or data views. A space must be in the configured registry before `space(id)` accepts it. These are reasonable choices for its sync use case, but they are policy a general administrative SDK may not want. [Endpoint modules](https://github.com/VimCommando/kibana-object-manager/blob/d75a3984b1875fb2d06afb9ab209a362d770d815/crates/kibana-sync/src/kibana/mod.rs), [public exports](https://github.com/VimCommando/kibana-object-manager/blob/d75a3984b1875fb2d06afb9ab209a362d770d815/crates/kibana-sync/src/lib.rs).

The repository documents ordinary mock tests and an ignored live suite. Its local live stack defaults to Kibana 9.3.3; licensed existing-server runs can exercise newer families. The documented family minima are agents/tools 9.2, workflows 9.3, and skills 9.4. These minima are not a broad promise that every operation works on every subsequent version. The inspected CI workflow runs preflight and MSRV checks; the presence of a live harness does not establish a continuously tested server matrix. [Live-test guide](https://github.com/VimCommando/kibana-object-manager/blob/d75a3984b1875fb2d06afb9ab209a362d770d815/crates/kibana-object-manager/docs/live-tests.md), [CI workflow](https://github.com/VimCommando/kibana-object-manager/blob/d75a3984b1875fb2d06afb9ab209a362d770d815/.github/workflows/preflight.yml).

**Recommendation:** contribute to or use this crate if the intended product is dashboard/artifact synchronization. For a typed administrative client, create a smaller independent API contract rather than taking a sync framework as a transport dependency. A shared transport extraction could be discussed later if both projects want it. No maintainer was contacted.

## Python: the most useful general-client reference

The current `kibana-py` README claims 39 namespaces and 610 endpoints covering platform, Fleet and Security Solution APIs, with sync/async parity. It includes dashboards and Lens visualizations, spaces, saved objects, alerting, connectors, cases, data views, SLOs and substantial security functionality. This is a community project, not an Elastic-supported SDK. These totals are the maintainer's inventory, not an independent operation-by-operation coverage audit. [README and coverage table](https://github.com/pedro-angel/kibana-py/blob/637922473bb5edeb3dfd5e3f9e1d177c34679069/README.md).

Inspected endpoint implementations manually assemble paths and dictionaries. I found separate sync and async source trees but no checked-in OpenAPI generator in the inspected build tooling. For example, dashboard methods return `ObjectApiResponse[Any]`. Python type hints and complete endpoint wrappers therefore do not establish the deeply typed request/response contract a Rust crate could offer. [Dashboard implementation](https://github.com/pedro-angel/kibana-py/blob/637922473bb5edeb3dfd5e3f9e1d177c34679069/kibana/_sync/client/dashboards.py), [build targets](https://github.com/pedro-angel/kibana-py/blob/637922473bb5edeb3dfd5e3f9e1d177c34679069/Makefile).

Its maintenance policy is worth copying in spirit. Supported versions live in one declaration, currently 9.5.4 and 9.4.7, representing the two latest minor lines. The release workflow derives its integration matrix from that declaration and blocks publication on failures. Older patches are expected to work, but are not the tested pins. Capability gates and additive response normalization handle observed differences. [Compatibility source](https://github.com/pedro-angel/kibana-py/blob/637922473bb5edeb3dfd5e3f9e1d177c34679069/kibana/_compat.py), [release workflow](https://github.com/pedro-angel/kibana-py/blob/637922473bb5edeb3dfd5e3f9e1d177c34679069/.github/workflows/release.yml), [version policy](https://kibana-py.readthedocs.io/en/stable/development/version-support.html).

A maintainer evidence report dated 2026-09-20 records 753 passed and 15 skipped on 9.5.4, and 752 passed and 16 skipped on 9.4.7. It also records four Fleet test failures on the initial patch upgrades, followed by investigation and fixture/assertion changes. This is concrete evidence that even patch updates need attention. These are published maintainer results; this research did not reproduce them. The release selection excludes tests marked flaky, so the README's broad live-tested claim should not be read as every endpoint succeeding under every environment. [Patch-upgrade evidence](https://github.com/pedro-angel/kibana-py/blob/637922473bb5edeb3dfd5e3f9e1d177c34679069/docs/evidence/multi-version-9.4.7-9.5.4.md).

## Go: limited community wrappers and a substantial Elastic reference

`disaster37/go-kibana-rest` declares Kibana 7.x and 8.x compatibility. Its current default branch is `8.x`, not `master`. Source exposes seven groups and 25 operations: spaces, roles, legacy dashboard import/export, saved objects, status, Logstash pipelines, and short URLs. The workflow starts Elasticsearch/Kibana 8.5.0, enables a trial, and runs tests. That is test infrastructure, not evidence of current 9.x support. [API declarations](https://github.com/disaster37/go-kibana-rest/blob/0b9a8c5ca23609d6ae0498e115ad988bf6fa9e6b/kbapi/api._.go), [workflow](https://github.com/disaster37/go-kibana-rest/blob/0b9a8c5ca23609d6ae0498e115ad988bf6fa9e6b/.github/workflows/workflow.yml), [dated head commit](https://github.com/disaster37/go-kibana-rest/commit/0b9a8c5ca23609d6ae0498e115ad988bf6fa9e6b).

Other discoverable Go choices include the `jloleysens` fork, whose latest v8 tag is 8.5.7 dated 2023-09-07, and `ottramst/go-kibana`, whose latest proxy version is dated 2022-02-07. Their registry histories were checked, but their endpoint implementations were not audited here. These are candidates for specific legacy needs, not evidence that a maintained comprehensive SDK is already available. [Fork metadata](https://proxy.golang.org/github.com/jloleysens/go-kibana-rest/v8/@latest), [ottramst metadata](https://proxy.golang.org/github.com/ottramst/go-kibana/@latest).

Elastic's Terraform provider is the stronger engineering reference. `generated/kbapi` contains an OpenAPI-generated client; `internal/clients/kibanaoapi` adds authentication, headers, configuration and endpoint helpers. The internal package is provider implementation, not a separately promised general-purpose SDK. The provider README claims Elastic Stack 8.0+, and its CI runs acceptance tests across a computed matrix, with snapshot failures treated separately. [Client factory](https://github.com/elastic/terraform-provider-elasticstack/blob/f59c1ddf44238ffe2ac00fefab210f7f53d0bd0f/internal/clients/kibanaoapi/client.go), [provider README](https://github.com/elastic/terraform-provider-elasticstack/blob/f59c1ddf44238ffe2ac00fefab210f7f53d0bd0f/README.md), [CI](https://github.com/elastic/terraform-provider-elasticstack/blob/f59c1ddf44238ffe2ac00fefab210f7f53d0bd0f/.github/workflows/provider.yml).

The generator uses an endpoint allowlist and repairs missing space parameters, content types, nested polymorphic schemas and endpoint-specific schema defects. Dashboard routes need a paths-only supplement because upstream entries are redirects. The README openly describes these obstacles and recommends fixing upstream issues. Its description of fetching `main` is stale: the inspected Makefile pins Kibana commit `d82496715d5f60ef9ba75126866c9ed801f31c03`. [Generation notes](https://github.com/elastic/terraform-provider-elasticstack/blob/f59c1ddf44238ffe2ac00fefab210f7f53d0bd0f/generated/kbapi/README.md), [actual Makefile](https://github.com/elastic/terraform-provider-elasticstack/blob/f59c1ddf44238ffe2ac00fefab210f7f53d0bd0f/generated/kbapi/Makefile).

Local line counts on the inspected snapshot were 1,999 lines for `transform_schema.go` and 289,500 for `kibana.gen.go`. Line counts are not effort estimates, but they show why generation does not remove schema-maintenance work. Some transformations address Go-generator limitations and may not be needed in Rust. [Transformer](https://github.com/elastic/terraform-provider-elasticstack/blob/f59c1ddf44238ffe2ac00fefab210f7f53d0bd0f/generated/kbapi/transform_schema.go), [generated code](https://github.com/elastic/terraform-provider-elasticstack/blob/f59c1ddf44238ffe2ac00fefab210f7f53d0bd0f/generated/kbapi/kibana.gen.go).

## JavaScript/TypeScript: distinguish a package name from a mature SDK

The inspected npm package `@gbaud/kibana-client` has 15 public methods, mostly cases and comments, plus connector lookup and rule search. Version 1.1.1 uses Axios; its published test file contains a single empty example test. Its metadata and README do not state a current Kibana version matrix. It is a narrow wrapper, not a strong design or maintenance baseline. The plain `kibana-client` npm name contains an unpublished 0.0.0 record, and `@elastic/kibana` returned 404 during this survey. That does not prove no other JavaScript client exists. [Package metadata](https://registry.npmjs.org/@gbaud/kibana-client), [published source archive](https://registry.npmjs.org/@gbaud/kibana-client/-/kibana-client-1.1.1.tgz), [unpublished package record](https://registry.npmjs.org/kibana-client).

## License facts and limits

`kibana-sync` declares Apache-2.0 in Cargo metadata. `kibana-py` declares Apache-2.0 in its project metadata. Elastic's Terraform provider has an Apache-2.0 LICENSE. `disaster37/go-kibana-rest` has an MIT LICENSE. The inspected npm package declares ISC. These are facts about those client repositories and packages. They do not establish the terms for copying Kibana's API documentation, schemas or server source. [Rust manifest](https://github.com/VimCommando/kibana-object-manager/blob/d75a3984b1875fb2d06afb9ab209a362d770d815/crates/kibana-sync/Cargo.toml), [Python metadata](https://github.com/pedro-angel/kibana-py/blob/637922473bb5edeb3dfd5e3f9e1d177c34679069/pyproject.toml), [provider LICENSE](https://github.com/elastic/terraform-provider-elasticstack/blob/f59c1ddf44238ffe2ac00fefab210f7f53d0bd0f/LICENSE), [Go LICENSE](https://github.com/disaster37/go-kibana-rest/blob/0b9a8c5ca23609d6ae0498e115ad988bf6fa9e6b/LICENSE).

The survey used primary registries, source archives and project-owned documentation. It cannot prove the absence of another client, assess maintainer willingness to collaborate, or establish real-world demand. The practical next step is to specify which automation tasks the Rust API should make safe and pleasant, then validate a small implementation against real pinned servers when implementation is authorized.
